# jsal.io

John Salvador's personal site: a home page and browser tools, plain HTML/CSS/JS with no build step, on GitHub Pages. `SETUP.md` is the human guide; this file is the working rules.

## Layout

- This folder is the repo `superjsal/jsal.io` (public); `site\` is what jsal.io serves. The "Deploy Pages" Action publishes `site\` on every push to `main`, live a minute or two later (Pages' source is "GitHub Actions", not a branch; `.github\workflows\deploy-pages.yml`). `private\` is ignored; `CLAUDE.md`, `SETUP.md` and `.claude\` are tracked but never served. Commit as superjsal <dev@jsal.io>.
  - Pages (styles inline unless noted):
    - Tools: `/cms-picker/` (CMS Picker, styles in `styles.css`), its 14 platform pages `/cms-picker/<platform>/` (written by the nightly publish from `.github\scripts\platform-page.html`; never edit them by hand), `/formatter/` (Clean Paste), `/image-resizer/` (Image Resizer), `/redirects/` (Redirect Import: a sheet of old and new addresses to each platform's redirect import file; the checks in `js\core.js`, each platform's format in `js\formats.js`), `/ic/` (Platform Playbook, team-only, noindex; its styles and script in `ic\styles.css` and `ic\app.js`).
    - Site: `/` (home: the tools, Updates and Say hi), `/play/` (Mostly Warcraft, "Off the clock" in menus: jsal.ui (the WoW UI), the WoW tile, the Backpack and the Achievements list), `/changelog/` (every change; noindex, not in the sitemap), `/privacy/`, `404.html`, and `/design-system/` (a showcase of the design rules; noindex, linked from nowhere).
  - Shared by every page:
    - `shell.css`: colour tokens `--jsal-*` (light and dark), the shared building blocks (corners, spacing, selected state, button weight), top bar, column width, page transitions, the achievement pop-up. Every page links it with one identical line, `<link rel="stylesheet" href="/shell.css?v=…">`, in `<head>` before the page's own styles (`check.py` checks the line and its place; its `?v=` is the file's content hash, like every other, see Before pushing).
    - `nav.js`: logo app menu, theme button, achievements, loading pages ahead on hover (speculation rules in Chrome and Edge, a plain prefetch in Brave and Firefox, which don't run them; Safari loads normally; the menu loads its pages ahead when opened), replaying clicks that land while pages change hands, and touch wording (`data-touch`, below). Each page loads it before its own deferred and module scripts (`check.py` checks), so the logo works before an app's modules arrive; clicks it replays on the page wait for the app's scripts.
    - A one-line `<script data-jsal-early>` in every page's `<head>` (after the favicon link) that holds a click landing before `nav.js` is ready, for `nav.js` to replay (without it a quick click after picking an app was lost, or the logo followed its plain link home), and on the first page of a visit folds the logo into its mark before the first paint, for `nav.js` to unfold. Copy it from `index.html` unchanged; `check.py` fails a page whose copy differs or is missing.
  - `.github\docs\` (not served): `how-it-works.md` (a map of the backend: Supabase, the publish, the Actions, the checks; keep it current when a moving part changes), `design-rules.md` (the design rules, imported below), `voice.md` (how the site writes: principles, say-this-not-that, tone by place; read it before writing copy), `manual-checks.md` (real devices and Firefox), `user-test-script.md` with `test-files\`, and `cms-picker-maintenance.md`.
- `.github\brand\` (not served): the logo (a lowercase j on a slate tile, its dot a gold gem; in the name the gem is the full stop and the j is drawn with round ends, the one soft letter): every SVG and PNG, `make-brand.py` that writes them and `site\favicon.svg`, and `README.md` with colours, clear space and where each file is used. The tile is for tabs and home screens; the top bar shows the name alone (real text, its "." drawn as the gem by `.jsal-stop` in `shell.css`), which unfolds from the mark on the first page of a visit (`nav.js`).
- `.github\build\` (in the repo, not served by Pages): the checks, the version bump, the share-image maker and Playwright's `package.json` (`npm ci` in that folder once per machine; `node_modules` isn't committed). The "Site checks" Action runs `check.py`, the data check, the personas and the browser checks (on Playwright's own Chromium, WebKit and Firefox) on every push to `main`, so every rule holds from any machine; the "Source links" Action asks each help page the Picker links to once a month (`.github\scripts\check_sources.py`). `.github\scripts\` holds `playbook.py` with `cms-picker.json` (the nightly publish), `check_data.py`, `personas.test.js`, `expert-cases.js` (a report on how often the quiz agrees with a consultant), `indexnow.py` and `updates.py` (the home page's Updates, from the changelog).- `private\` is never committed: `make-me-admin.sql`, SQL waiting for John to run, the latest Playbook backup (`backups\`; keep the newest one or two) and research notes with sources (`playbook-research\`). Off this PC, the "Back up Platform Playbook" Action keeps an encrypted copy of every table each Sunday as a workflow artifact for 90 days (`gh run download <run id> -n playbook-backup`, then `gpg --decrypt` with the `BACKUP_PASSPHRASE` secret's value, which John holds).
- `site\ic\supabase\schema.sql` builds the whole Playbook database from scratch (tables, access rules, admin functions) and is safe to re-run.
- `.claude\rules\` (not published): rules that load only for part of the site: `cms-picker-playbook.md`, `off-the-clock.md` (the WoW art rules), `image-resizer.md` (its history and the JScale names) and `analytics.md` (GA4 events and consent). `.claude\skills\add-tool\` is the checklist for adding a tool or page.
- Local preview: the `jsal-site` server in `.claude\launch.json` serves `site\` at http://localhost:8765.

- **Design or feature changes** (new looks, layout changes, new sections or tools): offer two or three mockups first for anything visual, build the one he picks, show it, and wait for his "commit and push". Small polish can be built straight away and shown.

- A message from John about something else while a task is mid-way: finish the step in hand, report where that task stands, then take the new thing. Don't drop verified-but-uncommitted work on the floor; say what's waiting and on what.

## Rules

- **Before pushing:** run `.github\build\check.ps1` and fix what it reports. With the local server running it also runs axe on every page (`browser-check.mjs --axe` next to it, Playwright in `.github\build\node_modules`, on the installed Edge); `node .github\build\browser-check.mjs` adds the 375/390px runs in Edge and WebKit. Playwright's own Chromium and Firefox don't start on this PC, so Firefox stays in `manual-checks.md`; the installed Firefox can still take a headless screenshot for a layout check (`"C:\Program Files\Mozilla Firefox\firefox.exe" -headless -no-remote -profile <scratch folder> --window-size=1280,1000 --screenshot <png> <url>`; the first screen only, taken before animations run, no scripting). From Claude Code these need the command sandbox off (the browsers can't start inside it). After changing `shell.css`, `nav.js`, `favicon.svg`, any app CSS/JS or `cms-picker/quiz.json`, run `.github\build\bump-version.ps1`. Every `?v=` is that file's own content hash (8 hex characters of its SHA-256), so the bump rewrites only the references to the files that changed, wherever they are: the pages, the apps' module imports and importmaps, `quiz.json`'s `data-quiz-v` on the CMS Picker's `app.js` tag, and `.github\scripts\platform-page.html`. A `shell.css` edit touches the shell link on every page (22 files); an edit to one app module touches that app's page and the modules that import it. Never hand-edit the numbers; `check.py` fails any reference whose hash isn't the file's current one. A new import between an app's modules carries `?v=` (`import … from "./x.js?v=0"`, then bump); `check.py` flags one without.
- **Committing:** work in a worktree of your own when the app offers one (the project folder is the repo, so it can): a worktree sees only its branch, so another session's half-done files can't end up in your commit, and the nightly Action's commits to `main` arrive when you merge. In this checkout, `git pull --ff-only` first, every time (the nightly Action commits to `main` too, and another chat may be working here at the same time). Stage files by name, never `git add -A`; after `bump-version.ps1`, that means every file it listed (only references to the changed files are rewritten, so a one-app change stays inside that app's folder; a `shell.css` or `nav.js` change touches every page and `.github\scripts\platform-page.html`). **Before bumping or committing, `git status` and `git diff --stat`:** if files you didn't edit are modified, another session is mid-change. Don't commit until it has committed (ask it with a message), and don't stage its files: a bump after its CSS/JS edits would rewrite their references with half-done contents' hashes. Subject as "Area: what changed" (e.g. "CMS Picker: round Compare button"), a plain-English body on why, then the co-author line. `CRLF will be replaced by LF` warnings are harmless.
- **Verify in the browser** at desktop width and 375px, in light and dark, before committing visual changes. The pane often runs in the background: page transitions and other animations don't play and screenshots can show an older frame, so check layout, colours and state by measuring with JavaScript, and say when the look itself wasn't seen. Take screenshots only as final proof or when the look itself is the question, at `scale: 0.5` unless fine detail is the point: each one is re-sent with every later turn of the session. For a change to a flow (the quiz to the comparison, a Show button, a save), tap through it at phone size and measure where each tap lands and how tall things are, not only the first screen: that's how the real pain points show up (a landing a screen below the result, 200px row cards, a 20px link).
- **Page transitions** (the slide itself is in the design rules' Motion section): `nav.js` sets `data-jsal-back` on `<html>` for Back. Every page's `.jsal-top` carries the logo caret and both theme icons in the HTML, not added by JS; the logo and theme button keep their own `view-transition-name`s and don't animate. Two elements with one name make the browser drop the transition silently.
- **Pages can load before they're shown** (`nav.js` prerenders a link's page on hover). Anything a page does on load that counts as a visit (an achievement, a counter) must wait for `prerenderingchange` when `document.prerendering` is true. Pages also come back from the back-forward cache exactly as they were left (`pageshow` with `persisted`): anything `nav.js` holds for a navigation in progress (held clicks, the open menu) must reset then, or the logo looks dead after Back.
- **Branding:** "jsal.io" or "John Salvador". Never a standalone "JSAL" (a well-known YouTuber uses it).
- **Comments in served files** (`site\`) explain the page to someone reading its source: what a block is and why it's built that way, in one or two lines above it. They never name tooling, scripts or folders outside `site\` (say "the publish", "regenerated", "the checks"), people, dates, a decision's history or TODOs; those belong in the changelog, the docs or the commit message. `check.py` fails a served comment that does (the scripts' marker comments are exempt). Keep a file's comment lines under about 15%.
- **About sections** (below each tool): say each thing once. A bold tagline (`jsal-lead`), then "How to use it"; any intro is one sentence; reference lists (what it checks, supports…) go in `<details>`, closed; two or three FAQs that the page doesn't already answer; then the Email me line and "Made by". The line under each tool's title (`jsal-for`) says who it's for.
- **Achievements:** to add one, add it to `ACH` in `nav.js` and call `window.jsalAchieve('id')` where it happens, then, in `site\play\index.html`, put it under its tool in `GROUP` (unlisted ones go under Around the site, secrets under Secrets) and give it a trophy in `TROPHIES` (a Blizzard item icon under `site\img\wow\`, see `.claude\rules\off-the-clock.md`; without one it drops a plain pouch). The pop-ups work on every page; the list and the Backpack's Trophies bag are on `/play/`. They're kept in each visitor's browser only; none on the team Playbook.
- **IndexNow** runs on its own (how-it-works.md); `python .github\scripts\indexnow.py <url>` (or `all`) is only for a page that changed without its file changing. The key file `site\184d9b76996d8751c72b4a5a062f80d7.txt` must stay.
- When something worth mentioning ships: add it at the top of `site\changelog\index.html` in one sentence of about 20 words, only if a visitor would notice it, and edit that day's line rather than adding another when the same feature changes again (the changelog rules in `voice.md`; small fixes share one "Small fixes: …" line a day) (under today's date heading, tagged with its app: CMS Picker, Clean Paste, Image Resizer, Redirect Import, Off the clock for `/play/`, or Site; a new tool gets its own tag). If it should lead its section in **Updates** on the home page, give its `<li>` a `data-short="…"` (about 40 characters, so it stays on one line at 1024px and up), then run `python .github\scripts\updates.py`: it rewrites the Updates block in `site\index.html` (between the `updates:start` and `updates:end` comments; never edit it by hand) with each section's newest `data-short` entry and date, in the order CMS Picker, Clean Paste, Image Resizer, Redirect Import, Off the clock, Site (`SECTIONS` in the script; a new tool goes there too). `check.py` fails when the block is out of date; the script warns past 40 characters. `/changelog/` is noindex and not in the sitemap.

## Working on this machine

- Windows. Large or multi-line edits through the shell break on quoting and backslashes: use the Edit tool, or write a small Python script to the scratchpad and run it with `python -I`. Run `.ps1` scripts from PowerShell.
- **Never put multi-line code or text inside a shell command** (no Bash heredocs, no `node -e`/`python -c` longer than a line, no `git commit -m` with quotes). The site's copy is full of curly quotes (’ “ ”) and backticks, which break the shell's quoting. Write the script or the commit message to the scratchpad with the Write tool first, then run it (`python -I file.py`, `node file.js`, `git commit -F msg.txt`).
- **One-off Playwright scripts** (screenshots, measurements, mockups with injected CSS) go in `.github\build\`, where Playwright is installed, run with the sandbox off, and get deleted afterwards (never committed); their screenshots and mockups go to the session's scratchpad, never into `site\`. Use `channel: 'msedge'` for Chromium. Run them from PowerShell: Edge doesn't start from the Bash tool. In this checkout, if `jsal-site` is already running from another chat, this session's own server may not answer; the running one serves the same folder and is fine to use.
- **Checks from a worktree:** port 8765 serves the main checkout, not the worktree, and `check.ps1` and `browser-check.mjs` test it silently; a worktree also has no `node_modules`. Serve the worktree yourself (`python -m http.server 8766 --directory site`, started hidden from PowerShell) and run `python -I .github\build\check.py` in the worktree for the static checks. For the browser part, copy `browser-check.mjs` into the main checkout's `.github\build\` with `BASE` set to `http://127.0.0.1:8766`, run it there (`node <copy> --axe`, PowerShell, sandbox off) and delete the copy. One-off Playwright scripts in a worktree load Playwright with `createRequire('C:/Users/JSAL/Desktop/jsal.io/.github/build/package.json')`.
