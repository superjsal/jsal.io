# jsal.io

John Salvador's personal site: a home page and browser tools, built with Astro (one shared layout; each app's own CSS and JS ship as plain files, unbundled), on Cloudflare. `SETUP.md` is the human guide; this file is the working rules.

## Layout

- This folder is the repo `superjsal/jsal.io` (public). Astro builds the pages in `src\` together with `site\` (every file they use: the apps' CSS and JS, images, fonts, data, `sitemap.xml`, copied as they are) into `dist\`, which is what jsal.io serves. Cloudflare builds every push from GitHub (`npm ci && npm run build`): a Worker named `jsal-io` with static files only, set in `wrangler.jsonc` at the root, with response headers in `site\_headers`. `main` is jsal.io, live within a minute; `staging` (and any other pushed branch) is a preview at `<branch>-jsal-io.still-cell-826b.workers.dev`, kept out of search and outside GA4. DNS is on Cloudflare too (the domain stays registered at Porkbun); www redirects to jsal.io by a Redirect Rule. A copy on GitHub Pages ("Deploy Pages", the same build; `site\CNAME`) is a fallback until 2026-11-09, then retired (delete the workflow, `site\CNAME` and the nightly publish's deploy step; John unpublishes Pages). `private\` is ignored; `CLAUDE.md`, `SETUP.md` and `.claude\` are tracked but never served. Commit as superjsal <dev@jsal.io>.
  - Pages, each in `src\pages\` (styles inline unless noted):
    - Tools: `/cms-picker/` (CMS Picker, styles in `styles.css`), its 14 platform pages `/cms-picker/<platform>/` (one `[platform].astro`, built from the published data; see the CMS Picker rules), `/formatter/` (Clean Paste), `/image-resizer/` (Image Resizer), `/redirects/` (Redirect Import: a sheet of old and new addresses to each platform's redirect import file; the checks in `js\core.js`, each platform's format in `js\formats.js`), `/ic/` (Platform Playbook, team-only, noindex; its styles and script in `site\ic\styles.css` and `site\ic\app.js`). An app's CSS and JS live in its folder under `site\`.
    - Site: `/` (home: the tools, Updates and Say hi), `/play/` (Mostly Warcraft, "Off the clock" in menus: jsal.ui (the WoW UI), the WoW tile, the Backpack and the Achievements list), `/changelog/` (every change, from the changelog collection; noindex, not in the sitemap), `/privacy/`, `404.html`, and `/design-system/` (a showcase of the design rules; noindex, linked from nowhere).
  - Shared by every page:
    - `src\layouts\Page.astro`: the document and the shared `<head>` (title and share card from the page's props, fonts, icons, the early click holder, analytics, the theme, `shell.css`, `nav.js`); a page adds its own styles and scripts in its `head` slot. `src\components\TopBar.astro`: the top bar (the logo, a tool's title, the page's links, the theme button). The Playbook lays out its own bar around the same logo and theme button (`src\lib\topbar.mjs`).

The layout links it before the page's own styles (`check.py` checks the built pages; its `?v=` is the file's content hash, like every other, see Before pushing).
    - `nav.js`: logo app menu, theme button, achievements, loading pages ahead on hover (speculation rules in Chrome and Edge, a plain prefetch in Brave and Firefox, which don't run them; Safari loads normally; the menu loads its pages ahead when opened), replaying clicks that land while pages change hands, and touch wording (`data-touch`, below). The layout loads it before a page's own deferred and module scripts (`check.py` checks), so the logo works before an app's modules arrive; clicks it replays on the page wait for the app's scripts.

Off this PC, the "Back up Platform Playbook" Action keeps an encrypted copy of every table each Sunday as a workflow artifact for 90 days (`gh run download <run id> -n playbook-backup`, then `gpg --decrypt` with the `BACKUP_PASSPHRASE` secret's value, which John holds).
- `site\ic\supabase\schema.sql` builds the whole Playbook database from scratch (tables, access rules, admin functions) and is safe to re-run.
- `.claude\rules\` (not published): rules that load only for part of the site: `cms-picker-playbook.md`, `off-the-clock.md` (the WoW art rules), `image-resizer.md` (its history and the JScale names), `redirect-import.md` (each platform's format, the checks and why they exist) and `analytics.md` (GA4 events and consent). `.claude\skills\add-tool\` is the checklist for adding a tool or page.
- Local preview (`.claude\launch.json`): `jsal-dev` is Astro's dev server at http://localhost:4321, which reloads as you edit; `jsal-build` serves the last build (`dist\`, after `npm run build`) at http://127.0.0.1:8766, the address the browser checks use. Run `npm ci` in the project folder once per machine (and once in each new worktree).

## Working with John

- **Small, low-risk fixes** (bugs, typos, data corrections, accessibility, hardening): build, verify, run the checks, then commit and push to `staging`, and tell him with the preview link. Pushing to `staging` changes nothing live.
- **Design or feature changes** (new looks, layout changes, new sections or tools): offer two or three mockups first for anything visual, build the one he picks, show it, and wait for his "commit and push" (to `staging`). Small polish can be built straight away and shown.
- **Shipping** is John's call ("ship it"): merge `origin/main` into `staging` (the nightly publish commits to `main`), push `staging`, then `git push origin staging:main`, which only fast-forwards. One push to `main` per batch, so one deploy, one run of the checks and one IndexNow ping. Changelog lines carry the day they ship; fix the date if a batch waited.
- It's a personal project: SEO work is correctness and quality (valid markup, metadata, accessibility), not growth tactics.
- A message from John about something else while a task is mid-way: finish the step in hand, report where that task stands, then take the new thing. Don't drop verified-but-uncommitted work on the floor; say what's waiting and on what.
- Browsers that matter: Brave (his), Chrome/Edge, Firefox. The preview pane is Chromium, so say when something Firefox-specific wasn't checked.

## Rules

- **Before pushing:** run `.github\build\check.ps1` and fix what it reports. It builds the site first (`npm ci` in the project folder once per machine) and checks `dist\`. With the build served (the `jsal-build` preview, port 8766) it also runs axe on every page (`browser-check.mjs --axe` next to it, Playwright in `.github\build\node_modules`, on the installed Edge); `node .github\build\browser-check.mjs` adds the 375/390px runs in Edge and WebKit. Playwright's own Chromium and Firefox don't start on this PC, so Firefox stays in `manual-checks.md`; the installed Firefox can still take a headless screenshot for a layout check (`"C:\Program Files\Mozilla Firefox\firefox.exe" -headless -no-remote -profile <scratch folder> --window-size=1280,1000 --screenshot <png> <url>`; the first screen only, taken before animations run, no scripting). From Claude Code these need the command sandbox off (the browsers can't start inside it). Every `?v=` is its file's own content hash (8 hex characters of its SHA-256). The pages need nothing: the build works out every `?v=` in a page as it builds (`v()` in `src\lib\v.mjs`, and `importmap()` for an app's import map). The apps' modules in `site\` import each other with `?v=` too, so after editing an app's JS module run `.github\build\bump-version.ps1`, which rewrites only the imports of files that changed. Never hand-edit the numbers; `check.py` fails any reference whose hash isn't the file's current one. The content security policy, which allows each inline `<script>` by its hash, is written into the built `dist\_headers` at the end of every build (`.github\build\csp.mjs`), so it always matches the pages; edit the policy there, never in `site\_headers`. A new import between an app's modules carries `?v=` (`import … from "./x.js?v=0"`, then bump); `check.py` flags one without.
- **Committing:** work in a worktree of your own when the app offers one (the project folder is the repo, so it can): a worktree sees only its branch, so another session's half-done files can't end up in your commit, and the nightly Action's commits to `main` arrive when you merge; merge a finished worktree branch into `staging`, not `main`. This checkout works on `staging`. In it, `git pull --ff-only` first, every time (the nightly Action commits to `main` too, and another chat may be working here at the same time). Stage files by name, never `git add -A`; after `bump-version.ps1`, that means every module it listed (it only rewrites imports, so a one-app change stays inside that app's folder). **Before bumping or committing, `git status` and `git diff --stat`:** if files you didn't edit are modified, another session is mid-change. Don't commit until it has committed (ask it with a message), and don't stage its files: a bump after its CSS/JS edits would rewrite their references with half-done contents' hashes. Subject as "Area: what changed" (e.g. "CMS Picker: round Compare button"), a plain-English body on why, then the co-author line. `CRLF will be replaced by LF` warnings are harmless.
- **Verify in the browser** at desktop width and 375px, in light and dark, before committing visual changes. The pane often runs in the background: page transitions and other animations don't play and screenshots can show an older frame, so check layout, colours and state by measuring with JavaScript, and say when the look itself wasn't seen. Take screenshots only as final proof or when the look itself is the question, at `scale: 0.5` unless fine detail is the point: each one is re-sent with every later turn of the session. For a change to a flow (the quiz to the comparison, a Show button, a save), tap through it at phone size and measure where each tap lands and how tall things are, not only the first screen: that's how the real pain points show up (a landing a screen below the result, 200px row cards, a 20px link).
- **Page transitions** (the slide itself is in the design rules' Motion section): the early script in the layout's head sets `data-jsal-back` on `<html>` for Back, before the first frame: from the Navigation API where it answers, else by comparing each page's place in the visit (`jsalAt` in its history state, kept through an app's `replaceState`; the page being left records its own in `sessionStorage`). Every page's `.jsal-top` carries the logo caret and both theme icons in the HTML, not added by JS; the logo and theme button keep their own `view-transition-name`s and don't animate. Two elements with one name make the browser drop the transition silently.
- **Pages can load before they're shown** (`nav.js` prerenders a link's page on hover). Anything a page does on load that counts as a visit (an achievement, a counter) must wait for `prerenderingchange` when `document.prerendering` is true. Pages also come back from the back-forward cache exactly as they were left (`pageshow` with `persisted`): anything `nav.js` holds for a navigation in progress (held clicks, the open menu) must reset then, or the logo looks dead after Back.
- **Branding:** "jsal.io" or "John Salvador". Never a standalone "JSAL" (a well-known YouTuber uses it).
- **Comments in served files** (the pages as built, and `site\`) explain the page to someone reading its source: what a block is and why it's built that way, in one or two lines above it. They never name tooling, scripts or folders outside `site\` (say "the publish", "regenerated", "the checks"), people, dates, a decision's history or TODOs; those belong in the changelog, the docs, an `.astro` file's frontmatter or the commit message. `check.py` fails a served comment that does. Keep a file's comment lines under about 15%.
- **About sections** (below each tool): say each thing once. A bold tagline (`jsal-lead`), then "How to use it"; any intro is one sentence; reference lists (what it checks, supports…) go in `<details>`, closed; two or three FAQs that the page doesn't already answer; then the Email me line and "Made by". The line under each tool's title (`jsal-for`) says who it's for.
- **Achievements:** to add one, add it to `ACH` in `nav.js` and call `window.jsalAchieve('id')` where it happens, then, in `src\pages\play\index.astro`, put it under its tool in `GROUP` (unlisted ones go under Around the site, secrets under Secrets) and give it a trophy in `TROPHIES` (a Blizzard item icon under `site\img\wow\`, see `.claude\rules\off-the-clock.md`; without one it drops a plain pouch). The pop-ups work on every page; the list and the Backpack's Trophies bag are on `/play/`. They're kept in each visitor's browser only; none on the team Playbook.
- **IndexNow** runs on its own (how-it-works.md); `python .github\scripts\indexnow.py <url>` (or `all`) is only for a page that changed without its file changing. The key file `site\184d9b76996d8751c72b4a5a062f80d7.txt` must stay.
- When something worth mentioning ships: add a line at the top of `src\content\changelog.json` (newest first, one entry per line: `{"date": "YYYY-MM-DD", "tag": "…", "text": "…"}`), one sentence of about 20 words, only if a visitor would notice it, and edit that day's line rather than adding another when the same feature changes again (the changelog rules in `voice.md`; small fixes share one "Small fixes: …" line a day). The tag is its app: CMS Picker, Clean Paste, Image Resizer, Redirect Import, Off the clock for `/play/`, or Site (`SECTIONS` in `src\lib\changelog.mjs`, in Updates order; a new tool goes there with its address and icon). Links are Markdown (`[Privacy](/privacy/)`); no HTML. If it should lead its section in **Updates** on the home page, add `"short": "…"` (about 40 characters, so it stays on one line at 1024px and up): Updates shows each section's newest `short` and its date, the three most recent. The build checks every entry (the schema in `src\content.config.mjs`): a bad date, an unknown tag or field, HTML, entries out of order or a section with no `short` stop it, naming the entry by its line; a line past 40 characters is a note. `/changelog/` is noindex and not in the sitemap.

## Working on this machine

- Windows. Large or multi-line edits through the shell break on quoting and backslashes: use the Edit tool, or write a small Python script to the scratchpad and run it with `python -I`. Run `.ps1` scripts from PowerShell.
- **Never put multi-line code or text inside a shell command** (no Bash heredocs, no `node -e`/`python -c` longer than a line, no `git commit -m` with quotes). The site's copy is full of curly quotes (’ “ ”) and backticks, which break the shell's quoting. Write the script or the commit message to the scratchpad with the Write tool first, then run it (`python -I file.py`, `node file.js`, `git commit -F msg.txt`).
- **One-off Playwright scripts** (screenshots, measurements, mockups with injected CSS) go in `.github\build\`, where Playwright is installed, run with the sandbox off, and get deleted afterwards (never committed); their screenshots and mockups go to the session's scratchpad, never into `site\`. Use `channel: 'msedge'` for Chromium. Run them from PowerShell: Edge doesn't start from the Bash tool. If `jsal-build` is already running from another chat, this session's own server may not answer; check which folder's `dist\` it serves before trusting what the checks report.
- **Checks from a worktree:** run `npm ci` in it once (the build needs Astro), then `check.ps1` as usual. Port 8766 serves whichever checkout's `dist\` started it, and the browser checks test whatever answers there, so serve the worktree's own (`python -m http.server 8766 --bind 127.0.0.1 --directory dist`, started hidden from PowerShell) after stopping any other. `browser-check.mjs` borrows the main checkout's Playwright when its own folder has none; one-off Playwright scripts in a worktree load it with `createRequire('C:/Users/JSAL/Desktop/jsal.io/.github/build/package.json')`.
