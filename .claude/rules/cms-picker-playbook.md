# CMS Picker and Platform Playbook

- **Active development (maintenance mode lifted 2026-10-31):** the quiz is the page's focus. Design changes still go through mockups first; a scoring change is agreed with John and keeps the personas passing (a persona that moves is agreed first); the data is corrected only through the content audit's findings he has agreed, never on a hunch. Parked ideas and the baseline are in `.github\docs\cms-picker-maintenance.md` ("Status").
- **Page structure:** the title and one line, then the quiz (`#quiz`), then two buttons (`.more-btn`) that open the platform cards (`#fit`) and the comparison table (`#seo`). Both sections are `hidden="until-found"`, so find-in-page opens them too; `setPanel`/`openPanel` in `app.js` open them for links to `#fit` or `#seo` (the platform pages' Compare button, the compare bar) and for the quiz's "Compare these side by side". Anything new that points into the cards or the table must open its panel first.
- **The quiz result carries into the table.** "Compare these side by side" on a result sets `state.quiz` in `app.js`: the three matches become the comparison with the best match as `state.pick`, each column's header gets its fit label, one gold line above the table (`#qz-line`) says why the best match is first (the first card's own box from `explain()`, "Why Wix first: …"), rows the answers rule out are dimmed (`weight() === 0` in `score.js`, and the cost rows that aren't `costRow(a)`) and fold to their label on phones, every section opens, and the page lands on the line. Any change to the comparison by hand (a chip, Select all, Clear, a goal) clears `state.quiz` and the table is plain again. "Only differences" (`#diffs`, remembered like Show notes) hides rows where every compared platform has the same tag, quiz or not. Keep all of this working together when touching the table or the result; the standard state for screenshots and measurements is `/cms-picker/#quiz?v=4&what=site&kind=local&who=easy&care=no&needs=none&look=visual&moving=no&budget=low` (Wix best match, Squarespace close second, Framer) and then "Compare these side by side".

- **What the Playbook is for:** John's team at a marketing agency (the SEO implementation side: web developers putting the SEO specialists' technical fixes and content on whatever CMS a client runs) uses it to fill out a capabilities record per client site in an internal HUB. **Its item headers match the HUB's headers one to one and must never be renamed or reordered**; answers and how-tos can be corrected, the structure can't. Judge its content by whether an implementer could trust it on a client site.
- **Where content lives:** Supabase is the source of truth. `app_data` holds the Playbook's base content, `edits` the admins' corrections on top, and the admin-only `picker` table every CMS Picker answer, source, profile and logo and which platforms are public. The CMS Picker keeps its own answers, separate from the Playbook's (a topic both cover, like meta titles, is labelled on each side and has to be corrected in both; each side's edit form has a "Copy from …" button that prefills from the other, nothing saved until Save). The page's code is `site\ic\index.html` (markup), `site\ic\styles.css` (its own styles, after the shared `/shell.css` link) and `site\ic\app.js` (a classic script, not a module: `nav.js` and the local test method below call its top-level names), linked with `?v=` content hashes like the other tools.
- **Day to day (admins, on the live page):** Edit on any answer; add, hide and restore platforms on the Team page (through the `add_platform` / `set_platform_hidden` functions; hidden platforms keep their answers); the admin-only **CMS Picker** tab (`#picker`) for its answers, sources, cards, logos and on/off switches, with what's waiting for the next publish.
- **Structural changes** (new item, page type or guide): `python .github\scripts\playbook.py pull`, edit `private\playbook\defaults.json`, `push`. Always pull first, so platforms added on the page aren't lost. The page shows built-in text as HTML, so `push` refuses a file with a stray `<` or an unknown tag in prose (write `&lt;`; only b, i, em, strong, code, a, br, p, ul, ol, li, span, kbd, small are allowed, and a guide block's `code` sample may hold anything); `playbook.py check` lints the file without pushing. Any script that writes Playbook text through the API must run `bad_html` on it first.
- **Publishing the CMS Picker:** `playbook.py publish` builds `cms-picker/data.json`, writes uploaded logos (cleaned SVG or PNG) to `cms-picker/logos/uploaded/` updates the plain-HTML copy in the page and writes one page per platform (`cms-picker/<platform>/index.html` from `.github\scripts\platform-page.html`, styled by `cms-picker/platform.css`, listed in `sitemap.xml`); never write those by hand. The nightly Action runs it at 07:41 UTC; `gh workflow run publish-cms-picker.yml` (from `site\`) publishes now. `scripts\cms-picker.json` sets the rows (each label a plain-language question finishing "Can you…", with its SEO name as `term`), the platform order; the Find my fit quiz's own values per platform (ease, design control, "Not ideal if" conditions and a few lists) are in `cms-picker/quiz.json`, which ships with the page code, not the publish (`app.js` fetches it with its own `?v=`, the `data-quiz-v` attribute on the script tag, which `bump-version.ps1` keeps current); everything else the quiz uses comes from the published answers and profiles. Hand-made logos stay in `cms-picker/logos/`.
- **CMS Picker data quality:** `cms-picker/data.json` must fit `.github\scripts\cms-picker.schema.json`; `check_data.py` (next to it) checks it before every publish, in `.github\build\check.ps1` and on GitHub, and reports answers with no source, sources over 90 days old, and anything not verified or unclear (`check_data.py --list` names them). Each answer's source (an official docs page) and its checked date live in the picker table's `sources` column, edited on the Playbook's CMS Picker tab; never add a source that isn't the platform's own documentation, and never guess one. How the CMS Picker's data, scoring wording (`TIP`, `PHRASE` in `score.js`) and tests fit together is in `.github\docs\cms-picker-maintenance.md`; keep it current when they change. The quiz's questions and scoring live in `cms-picker/score.js` (shared by the page and the tests); `.github\scripts\personas.test.js` runs agreed example people through it in `.github\build\check.ps1` and on GitHub. A failing persona means a result changed: agree the new result with John before editing its expectation. Shared quiz links carry `v=`; when the questions change, raise `LINK_VERSION` in `cms-picker/app.js` and translate older answers in `readLink` so shared links keep working.
- **Keep-awake:** free Supabase projects pause after about a week idle, so `keep-playbook-awake.yml` pings the database twice a week. If the Playbook ever says it couldn't load, check that Action's runs first.
- **Database changes:** write the SQL to `private\` and John runs it in Supabase → SQL Editor. Never run it yourself. Once he says it ran, add any structural part (tables, columns, functions, rules) to `schema.sql` so a rebuild still matches, then delete the one-off file. Data-only fixes just get deleted, because the backups have them.
- **Testing the Playbook locally:** in Playwright, block the Supabase script (`page.route('**/supabase-js@*/**', r => r.abort())`), open `/ic/`, then call `useContent(defaults)`, `applyShared({ edits: [], reqs: [], votes: [], members: [], notes: [] })` and `startApp({ name: 'Test' })`, with `defaults` read in Node from the latest backup's `app_data` row `defaults` (its `data`, plus `AT: updated_at`). Nothing is written into `site\`. Never load members, requests or other team data into a test page.
